# Baidu as a browser-fallback target

Baidu showed substantially better navigational relevance than Sogou on this Mac. Its browser fallback recovered real HTTP failures. Repeated requests eventually encountered persistent interactive verification on both transports, so the study does not support treating it as a reliable unattended replacement.

This was a temporary native Swift harness using the repository's SwiftSoup build, URLSession and WKWebView. No Baidu provider was added to the app or CLI. The earlier Sogou implementation remains unchanged.

## Technical corpus

The ten queries and expected URL substrings match the Sogou study. Results are limited to ten per query. MRR is the mean reciprocal rank over the eight queries with an expected URL; blocked queries count as zero. Latencies include successful responses only. Batches ran sequentially in the order below.

| Baidu batch | Valid / nonempty queries | Expected-URL MRR | Median | P95 |
| --- | ---: | ---: | ---: | ---: |
| HTTP | 7/10 | 0.500 | 1.22 s | 1.58 s |
| Browser | 8/10 | 0.500 | 1.59 s | 3.14 s |
| Automatic 1 | 6/10 | 0.625 | 1.13 s | 3.52 s |
| Automatic 2 | 0/10 | 0 | — | — |

In the first HTTP and browser batches, the expected SwiftSoup repository, Draw Things site, Swift site, and ArgumentParser GitHub result each appeared at rank 1. Automatic batch 1 recovered three HTTP failures through WebKit: the Apple `URLSession` site search, the Swift `PackageDescription` site search, and `latest Swift release`. All three recovered searches found the expected site at rank 1. That batch attempted seven browser fallbacks in total; the other four remained blocked.

Sogou's final comparison returned 10/10 valid responses, 7/10 nonempty queries and MRR 0 in every batch. Baidu's higher relevance comes with materially less stable availability in this run. Batch order and changing provider/session state prevent attributing all differences to transport alone or inferring an exact request-rate threshold.

The relevance improvement is selective. For example, Baidu's `OpenAI API docs` results began with a third-party API documentation site rather than the benchmark's expected official documentation URL, and the DuckDuckGo syntax query ranked SearXNG documentation first. Search success is not equivalent to an authoritative or relevant answer.

## Verification and Chinese queries

Verification became pervasive during the first automatic batch. The next ten automatic queries, followed by both six-query supplemental batches, all encountered verification. The supplemental set included Chinese official-site searches, Swift Chinese tutorials, `C++`, three-page pagination and an unlikely quoted query. Their result quality and pagination therefore remain unmeasured.

The main batches identified verification when Baidu navigated to `wappass.baidu.com` or displayed the `百度安全验证` page. To check whether this was merely a short automatic JavaScript check, a follow-up allowed the full 15-second browser timeout for `SwiftSoup GitHub` and `故宫博物院 官网`. Both remained blocked. The rendered page displayed an image-rotation slider with the instruction “拖动左侧滑块使图片为正”. No manual challenge completion was attempted, and challenge payloads or tokens are not included in the saved metrics.

## Integration implications

Baidu is a worthwhile next experimental provider if navigational relevance is the priority. An integration would need the same persistent web view and user verification flow, including the separate `wappass.baidu.com` origin, and validation that a completed challenge actually restores sustained searches. The current evidence does not establish that recovery or iOS behavior.

The observed result DOM exposes organic result titles under `#content_left .c-container h3 a` and destination metadata in the container's `mu` attribute. This allowed expected-site scoring without following Baidu's redirect links; the first browser batch had no unresolved redirect-only destinations. Empty responses must still be distinguished from verification and incomplete rendering.

The prototype is intentionally separate from production code. It does not establish complete parser coverage, cancellation behavior, safe-search or freshness-filter parity, or production fallback error policy. The recommendation is based on the measured relevance gain and the observed verification limitation, rather than readiness to replace the existing provider.
