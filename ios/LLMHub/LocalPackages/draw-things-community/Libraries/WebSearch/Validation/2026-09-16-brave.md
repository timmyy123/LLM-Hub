# Brave keyless search through WKWebView

Brave's public search site returned useful results through a native macOS
`WKWebView`, including separate-page pagination. Five consecutive requests
succeeded, followed by two HTTP 429 verification pages. A later follow-up using
the same persistent browser data succeeded again. This establishes feasibility,
but does not establish reliable unattended search.

The probe used the native WebKit user agent, JavaScript, and
`WKWebsiteDataStore.default()`, matching the existing DuckDuckGo browser approach.
It navigated to `https://search.brave.com/search` with `q`, `source=web`, and a
zero-based `offset`. Result URLs had to remain stable for four polls spaced
0.25 seconds apart. Each request had a 20-second deadline. No API key or manual
challenge completion was used, and result destinations were not fetched.

| SwiftSoup GitHub | 0 | 200 | 20 | 1.51 |
| Draw Things app | 0 | 200 | 20 | 1.27 |
| site:developer.apple.com URLSession | 0 | 200 | 20 | 2.26 |
| Swift programming | 0 | 200 | 20 | 2.26 |
| Swift programming | 1 | 200 | 20 | 1.26 |
| C++ 参考手册 | 0 | 429 | verification | 20.01 |
| Quoted unlikely query | 0 | 429 | verification | 20.01 |
| SwiftSoup GitHub (later follow-up) | 0 | 200 | 20 | 1.51 |

The first results matched the expected SwiftSoup repository, Draw Things website,
Apple URLSession documentation, and Swift website. The two Swift programming
pages contained 40 distinct URLs with no overlap. One preliminary HTTP request
also returned a populated public search page; this was not an HTTP benchmark.

The result DOM exposed `.snippet[data-type="web"]`, titles under `.title`,
destination links as the title's ancestor `a`, and descriptions under
`.generic-snippet .content`. Pagination exposed a Next link with `offset=1`.
These selectors avoid Svelte's generated class names, but remain site markup
that Brave can change.

The blocked pages said “Verifying you're not a bot” and offered a Verify button
and a traditional CAPTCHA option. They remained verification pages for the full
20-second observation window; they must be reported as challenges, not empty
search results. The later successful request suggests the block can clear, but
this sequence cannot determine a rate limit or guarantee recovery.

A production browser route would need the existing shared WebKit request queue
and challenge presenter, plus Brave-specific result parsing, query/page identity
checks, pagination, and explicit empty/challenge detection. Recovery after manual
verification, cancellation, freshness/safe-search options, and iOS behavior remain
unverified. The API integration therefore retains Kagi's explicit missing-key
error; no browser fallback is silently selected.

## API integration verification

The callback-based `BraveSearch` implementation was tested separately with an API
key supplied for this task. The live Bazel smoke test returned one result for
`Draw Things app`. A native probe linked against the rebuilt WebSearch library
returned 25 unique results across two pages for `Swift programming`, and three
results for `C++ programming` with the week freshness filter. The latter verifies
successful request handling, not the underlying documents' publication dates.

The WebSearch suite ran 66 tests with no failures; the optional Kagi live test was
skipped because no Kagi key was supplied. The focused Local Code CLI settings
regression test also passed, covering provider parsing and missing, blank, and
trimmed API keys. `WebSearchCLI` and the Local Code iOS arm64 library built
successfully. The full app bundle build failed in the existing
`ios_system` framework link with an undefined `_ios_python_register_mlx` symbol.
The supplied API key is not included in source or validation artifacts.
